# 저장된 기억 전수 감사와 다음 방향

작성일: 2026-09-04. 검토 대상 구현: `005b97cd220a6eceb084720aa5657555a1686584`.

현재 구현은 실행·저장·재개·비용 관리의 동작을 확인했지만, 생성된 기억의 품질은 아직 충분하지 않다. 다음 작업의 우선순위는 **관찰의 맥락 보존 → 반복 생성 방지 → 관계의 근거 판정 → 통제된 재평가**다. 더 높은 depth나 더 많은 기억을 만드는 것을 목표로 삼지 않는다.

이 문서는 실제 결과를 읽고 작성한 감사와 제안이다. 기존 보완 설계의 확정 사항을 변경하는 문서는 아니다.

후속 기록(2026-09-05): 발화 하나로 입력 단위를 바꾼 대응도 맥락 부족을 해결하지 못한다는 사용자 지적을 반영했다. 새 실험은 **세션 전체를 raw 하나로 전달하고 그 맥락에서 복수 observation을 추출**한다. 같은 Source의 root는 하나다. 본문의 52개 기억과 통계는 변경 전 v1 파일럿의 감사 기록으로 보존한다.

## 조사 범위

프로젝트 안에서 발견한 SQLite 저장소 6개를 읽었다. Phase 5 파일럿 저장소 5개에 기억 52개, 이전 관찰 UI 검증 저장소에 수동 fixture 35개가 있다. 총 87개의 본문을 확인했다.

품질 평가는 실제 모델이 생성한 파일럿 기억 52개 전체에 대해 수행했다. 모든 본문을 원래 대화 4개 발화, 분할 raw 15개, 부모 기억, 관계 5개, 생성 작업 기록, 최종 답변 근거와 대조했다. `graph.json`의 52개 ID·본문·depth는 SQLite와 일치했고, 네 기억 조건에 저장된 Source 60개는 동일한 raw 15개의 사본이었다.

UI fixture는 `TestResults/inspection-review/Program.cs`에서 `review-fixture`라는 모델명으로 직접 넣었다. depth 0 31개, depth 1 3개, depth 2 1개다. 번호만 다른 반복 문장, HTML 표시 검증 문자열, 수동 추상 기억이므로 모델의 기억 품질 통계에 포함하지 않았다. 35개 전부 별도 목록에 기록했다.

## 1. 입력이 관찰 단위가 아니라 구두점 단위로 잘렸다

네 발화가 15개 raw로 분할됐다. 그중 네 개는 본문이 각각 `1. `, `2. `, `3. `, `4. `뿐이다. 목록 번호 뒤의 마침표를 문장 끝으로 인식하여 설명에서 떼어냈기 때문이다. 이 네 조각을 네 기억 조건에서 각각 Remember에 보내므로, 의미 없는 목록 번호에만 추출 요청 16회가 발생했다. 이 숫자는 전체 185회 중 일부이며 별도의 비용 절감액을 추정한 것은 아니다.

사과, 목록 도입부, 마지막 인사도 각각 분리됐다. 원문을 이어 붙여 정확히 복원할 수 있다는 사실만으로 입력 단위가 적절한 것은 아니다.

| raw | 원문에서 하는 일 | Remember / Dream / Relations / Meditation 저장 결과 |
| --- | --- | --- |
| S01 | 사용자의 “그게 더 길잖아” | 모두 저장 |
| S02 | assistant의 오해에 대한 사과 | Dream만 저장하지 않음 |
| S03 | 더 짧은 표현으로 sexual compulsions 제안 및 설명 | 모두 저장 |
| S04 | 사용자의 “더 나은 걸 생각해봐” | 모두 저장하지 않음 |
| S05 | 앞선 제안이 도움되지 않았다면 사과 | 모두 저장하지 않음 |
| S06 | 다른 대안을 제시한다는 도입부 | 모두 저장하지 않음 |
| S07 / S09 / S11 / S13 | 목록 번호 네 개 | 모두 저장하지 않음 |
| S08 / S10 / S12 / S14 | 네 대안의 이름과 설명 | 모두 저장 |
| S15 | 도움이 되길 바란다는 끝인사 | 모두 저장하지 않음 |

모든 조건에서 정답에 필요한 다섯 용어는 살아남았다. 그러나 “처음 제안 → 사용자의 추가 요청 → 네 대안”이라는 연결은 기억에서 약해졌다. S01은 대상 없는 인용으로 남고, S04와 목록 도입부는 사라졌다. 사람의 지속적인 선호를 추론할 자료도 아니다.

또한 D02·M03은 원문의 “더 짧은 표현으로 제안했다”를 “그 행동을 이렇게 설명했다”로 바꾸었다. 용어를 제안한 사건과 대상 행동에 대한 판단은 구분해야 한다.

**제안:** 목록 번호와 항목을 함께 유지하고, 각 항목이 무엇에 대한 제안인지 알 수 있는 최소 맥락을 보존한다. `remember(raw)`의 발언자·프로젝트 validation을 추가할 필요는 없다. 입력을 만드는 adapter나 호출자가 관찰 하나의 의미를 닫아 주는 책임이다. 맥락을 제공할 때도 다른 관찰의 내용을 독립적인 새 근거인 것처럼 복제하지 않아야 한다.

## 2. 상위 기억 네 개가 대화 순서를 뒤집었다

원문의 실제 순서는 다음과 같다.

1. 사용자: `thats actually longer`
2. Assistant: 오해해서 미안하다고 말한 뒤 `sexual compulsions`를 더 짧은 표현으로 제안
3. 사용자: `come on think in something better`
4. Assistant: 다른 네 표현 제안

Relations 조건의 아래 기억들은 1번 발언을 2번 이후의 반응으로 재구성했다.

| 기억 | 잘못 추가된 연결 | 전체 ID |
| --- | --- | --- |
| L10 | sexual compulsions 제안 → 사용자가 길다고 반응 → 나중에 사과 | `mem_71e6732b672a4889af3eb2d5b4e70e4a` |
| L13 | 용어 제안 뒤 사용자가 길다고 말했다고 기술 | `mem_a0985860afd8433c9544a489f27ab027` |
| L15 | 제안 → 반응 → 사과를 실제 conversational correction으로 단정 | `mem_98a825f419ea4e6d9670d692d6d7d252` |
| L17 | 해당 제안보다 나중에 길다는 발언이 있었다고 기술 | `mem_cad309a4f05c482ba9e0cc7e9ed29802` |

실제로 사용자가 길다고 평가한 앞선 표현은 제공된 대화에 없다. “possible”, “대상은 확실하지 않다” 같은 유보를 붙여도 이미 뒤집은 순서가 정확해지지 않는다. 이 네 기억은 이번 최종 답변에는 선택되지 않아 정답 판정에서 문제가 드러나지 않았다.

원인을 좁히면 다음 사실이 확인된다.

- adapter가 모든 raw에 같은 세션 시각을 붙인다. 이 문항의 depth 0 `created_at`도 모두 같다.
- 원본의 `turn_index`와 `part_index`는 별도 매핑 파일에는 있으나 모델에 전달되는 기억에는 없다.
- `PromptMemory`는 `Sequence`와 원본 발화 순서를 제공하지 않는다. Dream은 raw도 읽지 않는다.
- 추상화 입력은 검색 결과 순서로 배치되고, 같은 생성 시각의 작업 순서는 임의 Memory ID로 결정된다. 어느 쪽도 사건 순서가 아니다.

순서 정보가 없는 입력을 주고 관계를 복원하게 만든 뒤, 원문과의 시간적 일치 여부를 검증하지 않았다. 모델은 그 빈칸을 그럴듯한 이야기로 채웠다. 이는 모델의 실수와 입력·검증 설계의 결함이 함께 나타난 결과다.

**제안:** 알려진 원본 발화 순서는 보존하되 시간을 임의로 만들어 붙이지 않는다. benchmark에서 정답을 노출하는 세션 ID 대신 중립적인 위치 표현을 사용할 수 있다. 일반 입력에서 사건 순서를 알 수 없다면 저장 순서나 배열 순서로 대체하여 추론하지 않게 한다. `created_at`은 계속 내부 생성 시각이며 사건 시각의 대용물이 아니다.

## 3. 대부분의 상위 기억은 같은 비교를 반복한다

depth 1의 25개를 읽고 다음과 같이 분류했다. 이는 사람의 정성 검토이며 자동 중복 점수가 아니다. 조건끼리 저장소가 다르므로 조건 간 비슷한 결과 자체를 중복 저장 결함으로 세지 않았다.

| 분류 | 수 | 기억 |
| --- | ---: | --- |
| 같은 용어 비교 묶음을 범위·표현만 바꾸어 반복 | 19 | D07~D12, L08·L09·L11·L12·L14·L16, M08~M14 |
| 발화 순서 오류 포함 | 4 | L10·L13·L15·L17 |
| 추가적인 구분·미해결점 후보 | 2 | M15·M16 |

19개 전부가 쓸모없다는 뜻은 아니다. 다섯 표현을 통제의 어려움·몰두·생활상 어려움으로 비교하는 기억 하나는 탐색에 유용할 수 있다. 문제는 같은 조건 안에서 그 비교를 여러 번 별도 기억으로 저장한 것이다. 부분집합 비교와 조건 표현의 작은 차이는 있지만, 별개의 발견 19개라고 보기는 어렵다.

일부 표현은 원문보다 더 나아갔다. 예를 들어 “교환 가능하다는 근거가 없다”와 “교환 불가능하다”는 다르다. L12·M11은 후자처럼 단정했고, D11·L11은 용어별 조건을 묶어 쓰면서 적용 범위를 넓힐 여지가 있다. 정확한 조건과 그 조건이 속한 대상을 함께 보존해야 한다.

### 생성 작업에서 확인한 중복 원인

저장된 `run_work.proposal_json`의 후보 ID를 순서 없이 비교했다.

| 실행 | 같은 후보 집합에 대한 추상화 요청 | 결과 |
| --- | ---: | --- |
| Dream 조건의 Dream | 기억 6개 집합을 6번 | D07~D12 6개 |
| Relations 조건의 Dream | 기억 7개 집합을 7번 | L08~L17 10개 |
| Meditation 조건의 Dream | 기억 7개 집합을 7번 | M08~M14 7개 |
| Meditation 조건의 주간 실행 | 기억 12개 집합을 7번 | M15·M16 2개, 나머지 5번은 빈 결과 |

각 seed마다 검색하지만 작은 corpus에서는 매번 같은 전체 기억 집합이 반환된다. `AbstractAsync`에는 seed가 어떤 기억인지 별도로 전달하지 않는다. 결국 같은 기억들을 배열 순서만 바꾸어 다시 분석하게 된다. 실제로 D01처럼 대상 없는 짧은 발언을 seed로 한 작업에서도 그 발언을 부모로 쓰지 않는 용어 요약이 만들어졌다.

생성 근거는 실행 시작 시점의 고정 snapshot이다. 따라서 같은 실행에서 먼저 만든 요약을 다음 요청은 보지 못한다. 현재 프롬프트에도 일반 요약과 기존 기억의 재서술을 피하라는 문장이 있지만, 이 상황을 막지 못했다. 프롬프트 문장 하나를 더 추가하는 것만으로 해결했다고 볼 수 없다.

**제안:** 먼저 같은 역할·근거 snapshot·맥락에서 후보 집합까지 동일한 작업을 묶어 처리하고, 다룬 seed를 기록한다. 모든 Dream 대상은 여전히 처리하되 API 호출을 반드시 대상 수만큼 반복할 필요는 없다. 부분적으로 겹치는 다른 근거까지 무조건 합치는 hard clustering은 도입하지 않는다.

또한 기존 기억 및 이번 실행에서 이미 수용한 제안을 중복 비교용으로 볼 수 있어야 한다. 단, 이번 실행의 출력은 새로운 추상화의 부모나 증거로 사용하지 않는다. 근거 snapshot과 중복 비교 대상을 명확히 분리하고, 재개해도 같은 판정이 유지되도록 저장해야 한다.

의미 유사도는 비교 후보를 찾는 데만 사용한다. 비슷한 표현이라도 반례·조건·대상이 달라질 수 있으므로 임계값 하나로 자동 삭제하지 않는다. 새 제안을 저장할 이유는 “어떤 구분이나 관계가 추가되었는가”로 설명할 수 있어야 한다. 없으면 빈 결과로 정상 완료한다.

## 4. 양의 관계 다섯 개는 지지 근거가 충분하지 않다

현재 Assimilation 프롬프트는 단순 유사성으로 관계를 만들지 말라고 한다. 저장된 관계를 그 기준으로 다시 읽으면 다음과 같다.

| 방향 | 내용 | 검토 |
| --- | --- | --- |
| M02 → M01 | 사과했다 → 사용자가 길다고 말했다 | 길다는 피드백은 사과가 실제로 있었다는 주장 자체를 뒷받침하지 않는다. 관련 맥락과 명제의 증거를 혼동했다. |
| M03 → M06 | sexual compulsions 설명 → sexual impulsivity 설명 | 서로 다른 용어의 설명이 겹친다는 사실만으로 앞의 설명이 지지되지 않는다. |
| M03 → M07 | sexual compulsions 설명 → compulsive sexuality 설명 | 같은 문제다. |
| M06 → M07 | sexual impulsivity 설명 → compulsive sexuality 설명 | 설명의 유사성을 지지 관계로 바꿨다. |
| M07 → M06 | compulsive sexuality 설명 → sexual impulsivity 설명 | 반대 방향에서도 동일한 문제가 반복됐다. |

다섯 개 모두 `related_at = 2023-05-24T00:00:00+00:00`을 가지고 있으며, Meditation 조건의 **앞선 Dream Assimilation**에서 생성됐다. 주간 Meditation이 만든 관계가 아니다.

M06 ↔ M07은 코드가 역방향을 자동 복제한 결과가 아니다. 서로 다른 focal observation을 처리한 두 요청에서 각각 제안했다. 따라서 해결할 문제는 역방향 탐색 기능이 아니라 각 방향의 의미적 근거 판정이다.

**제안:** 관계를 제안할 때 “A의 어느 주장에 B의 어느 내용이 지지·반례가 되는가”를 구체적으로 설명할 수 있어야 한다. 출력에 짧은 이유를 남겨 검토 가능하게 하는 방법도 고려한다. 같은 주제, 같은 표현, 서로 다른 용어의 비슷한 설명만 있다면 관계를 만들지 않는다. 단방향 저장과 조회 원칙은 유지한다.

## 5. Meditation의 성과와 depth를 해석하는 방법

M15는 통제 어려움과 생활상 영향이 모든 용어에서 똑같이 주장되지 않았음을 짚었다. 특히 어떤 설명은 영향을 조건부로만 언급하고 어떤 설명은 어려움 자체를 중심으로 정의한다는 차이를 보존했다.

M16은 impulsivity의 설명 자체에 impulsive와 compulsive가 함께 들어가므로 이 대화에서 용어 경계가 명료하지 않다고 짚었다. 이것을 확정적인 외부 지식이 아닌 대화 속 용어 사용에 관한 가설로 한정한 점이 적절하다.

두 기억은 더 검토할 가치가 있다. 다만 새 외부 증거가 추가된 것은 아니며, 이번 질문의 최종 근거에는 둘 다 선택되지 않았다. 따라서 답변 품질을 개선했다고 주장할 수 없다.

둘 다 depth 0에서 직접 derive한 depth 1이다. Meditation이라고 자동으로 한 층 더 올라가지는 않는다. 주간 실행에 제공된 기존 depth 1 일곱 개의 root 합집합은 **5개**다. B=3에서 depth 2에 필요한 서로 다른 Source는 9개이므로, 이 근거에서 depth 2가 나오지 않은 것은 정상이다. 제약을 낮추거나 부모 수를 root 수처럼 세어 해결할 문제가 아니다.

주간 Meditation은 7번의 추론과 2번의 새 기억 임베딩에 총 **0.15398834달러**를 썼다. 다섯 추론은 빈 결과였으며 상한 5달러를 채우려는 추가 작업은 없었다. 지금은 예산을 낮추는 것보다 이미 처리한 근거를 반복 분석하는 구조를 먼저 고치는 편이 낫다.

## 6. 정답률 외에 봐야 할 품질

Remember 조건의 답변 근거는 본문 기준 991자였다. Dream은 1,254자, Relations는 1,271자, Meditation은 1,290자였다. FullHistory의 원래 네 발화는 1,178자였다. 이는 토큰·JSON·프롬프트 길이가 아닌 근거 본문 문자 수 비교다.

상위 기억이 있는 세 조건은 각각 요약 하나와 정답 네 항목의 depth 0을 함께 선택했다. 요약에도 같은 네 용어가 있으므로 내용이 일부 반복됐다. 같은 정답을 위해 기억 시스템이 항상 더 짧은 근거를 제공한 것은 아니다. 다만 이 질문 하나에서 선택되지 않았다는 이유로 모든 다른 기억이 무용하다고 판단할 수는 없다.

현재 지표의 빈틈도 확인했다.

- 완전히 같은 문자열의 추상 기억은 0개지만 의미 중복은 많다.
- 부모·root·depth 검사는 모두 통과했지만 시간 순서 오류는 네 개 있었다.
- 정답 세션 회수율은 100%지만 원문 발화 관계가 정확히 보존되었다는 의미는 아니다.
- 조건마다 Remember를 독립 실행하여 depth 0이 6개 또는 7개였다. 이후 결과 차이를 Dream/Relations/Meditation만의 효과로 분리할 수 없다.
- Relations 조건에서는 관계가 없고 Meditation 조건에서만 관계가 생긴 차이 역시 주간 Meditation의 효과로 해석할 수 없다. 두 조건의 Dream 호출 결과부터 달랐다.

## 다음 작업 제안

### 첫 번째: 입력과 시간 관계를 바로잡는다

목록 구조를 깨는 분할을 고치고, 관찰 하나가 이해 가능한 최소 맥락을 갖게 한다. 원본 발화 순서와 사건 시각, 시스템 저장 시각을 구분한다. 이번 네 순서 오류와 '제안 → 판단' 변형을 재현 사례로 남겨 수정 효과를 확인한다.

### 두 번째: 새로운 내용이 없으면 추가하지 않게 한다

동일 근거를 반복 제출하는 작업부터 합치고, 생성 단계에서 비교용 기존 결과를 볼 수 있게 한다. 모든 대상 처리와 모든 대상에서 새 기억 생산을 구분한다. 상위 기억 하나는 원문들을 함께 봤을 때 얻는 비교·조건·예외·미해결점을 담을 수 있지만, 같은 비교의 여러 재서술은 별개 성과가 아니다.

출력 개수의 고정 목표나 의미 유사도만으로 기존 기억을 지우는 정책은 도입하지 않는다. 이미 생성한 파일럿 기억은 감사 자료로 보존하고, 수정 후 새 실험 저장소에서 비교한다.

### 세 번째: 관계와 평가를 함께 정밀하게 만든다

관계의 주장·근거 대응을 확인하고 단순 유사성을 걸러낸다. 기능 효과를 비교하는 실험에서는 가능한 공통 단계의 결과를 고정하여 조건을 분기하고, 공유 비용도 별도로 설명한다. 시계·원문·provenance는 유지하며 질문이나 정답을 사전 기억 과정에 넣지 않는다.

이후 작은 검증 사례를 먼저 사용한다. 같은 원문의 반복 분석, 순서가 있는 수정 대화, 조건부 예외, 실제 반례, 충분한 별도 관찰이 있는 depth 2 사례, Recall 이후 다음 Dream의 처리까지 포함한다. depth 2 사례에서도 B=3과 서로 다른 Source 9개 이상이라는 제약을 그대로 지킨다. 작은 사례가 통과한 다음 여러 유형의 LongMemEval 문항으로 넓힌다.

비교할 값은 정확한 답변뿐 아니라 원문 충실도, 새롭게 구분한 내용, 조건 내 중복, 관계의 근거 적합성, 답변에 실제 쓰인 근거와 비용이다. 기억 수·최대 depth가 늘어나는 것은 그 자체로 성공 지표가 아니다.

## 감사 당시 유지 대상으로 적었던 사항

하나의 공유 기억 공간, 관찰 크기의 raw, 내부 `created_at`, 동일 raw의 코드 수준 중복 방지, Source 하나당 root 하나, 기하급수 root 제약, 같은-depth 부모, 단방향 관계, Dream 대상 전수 처리와 무제한 예산, 주간 Meditation 최대 5달러는 유지한다. Source 수와 별개로 같은 대화에서 나온 근거라는 맥락을 함께 해석하되, root 단위를 세션으로 바꾸지는 않는다.

이번 감사에서 추가한 것은 문서와 읽기 전용 분석 자료뿐이다. 실행 코드와 저장된 기억에는 변경을 가하지 않았다.
후속 정정: 위 절의 “관찰 크기의 raw”와 “root 단위를 세션으로 바꾸지는 않는다”는 당시 판단이다. 사용자 지적 이후에는 대화 세션 전체가 raw 하나이므로 해당 세션 Source가 root 하나가 된다. 2026-09-05에 변경한 입력 코드와 실제 모델 재실행은 [세션 실험 결과](13-session-pilot.md)에 별도로 기록한다.

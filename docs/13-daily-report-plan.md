# 실사용 Daily Report 작업계획

상태: 사용자 승인 후 구현 완료. 아래는 구현 전 합의한 계획이며, 실제 사용법과 기록의 의미는 [Daily Report 안내](14-daily-report.md)에 정리했다.

## 목적

에이전트가 실제로 선택한 Remember 입력이 observation 수, Recall, Assimilation 작업량과 비용으로 어떻게 이어지는지 사후 분석한다. 다음 연결을 호출·Source·Memory·Dream work ID로 따라갈 수 있게 한다.

`remember 호출 → raw Source → 생성된 D0 → recall 반환 / assimilation → 실제 추가된 관계`

관계가 추가됐거나 기억이 반환됐다는 사실만으로 유용했다고 판정하지 않는다. 이 기록으로는 에이전트가 Remember하지 않은 경험이나 답변에 기억을 실제로 사용했는지는 알 수 없다.

## 1. 기록 단위와 항목

### Remember

- 호출 ID, 시작·종료 시각, 성공·실패·취소·미완료 상태와 오류 유형.
- raw의 UTF-16 문자 수와 UTF-8 byte 수. 문자 수를 token 수로 취급하지 않는다.
- 연결된 Source ID와 원문 파일 경로. 원문은 기존 Source archive를 이용한다.
- 신규 Source 수용 여부, 기존 Source 재사용 여부, 추출 수행 여부를 별도 기록한다.
- 추출 시도 ID, 생성된 D0의 ID·내용·생성 시각·모델, 호출이 반환한 D0 ID.
- 에이전트 호출과 백그라운드 Source 복구를 구분한다. 복구가 Remember 호출 횟수를 늘리지 않게 한다.
- 중복 입력으로 기존 D0가 반환된 경우와 새 D0가 생성된 경우를 구분한다. 0개 추출, 입력 거부, 추출 중인 Source에 대한 재호출도 기록한다.
- 계측 경계는 MemoryEngine 호출 진입 시점으로 잡아 입력 크기 검증 거절도 포함한다. 메서드에 도달하지 못한 MCP 전송·인자 파싱 오류는 이 호출 수에 포함하지 않는다. raw가 없으면 크기는 unknown으로 남긴다.
- 중복을 포함한 제출 raw 총량과 신규 저장된 고유 Source 총량을 따로 집계한다. 서버 측 완료 기록은 클라이언트의 응답 수신을 보장하는 지표가 아니다.

현재 `RememberResult.Duplicate`만으로는 분석하지 않는다. Source claim에 실패한 호출에는 다른 호출이 추출 중인 경우도 포함되므로 Source 상태와 추출 시도를 함께 본다. 수용되지 않은 raw는 Source가 없을 수 있고, 이때 원문을 별도로 저장하기보다 입력 크기와 거부 사유를 남긴다.

### Recall

- 호출 ID, 시작·종료 시각, query·context, 결과 상태.
- 당시 검색 후보 ID와 순서, 최종 선택·반환 ID와 순서. 기억의 immutable content·depth·Source는 이 ID로 연결한다.
- 반환 D0의 전체 횟수와 고유 개수를 모두 집계한다. 같은 D0의 반복 반환을 보존하고 높은 depth 반환도 별도 기록한다.
- 후보 0개, 후보는 있지만 선택 0개, 실패한 호출을 구분한다.
- 현재 relations나 last_recalled_at을 조인하여 당시 검색 맥락인 것처럼 표시하지 않는다. v1의 후보 기록은 당시 ID·순서이며 전체 모델 프롬프트 재현 기능은 아니다.

### Assimilation

- 논리 작업의 `run_id / work_key / seed D0 ID`, 대상 Dream 기간, 실제 실행 시각.
- 실행 시도, 실제 모델 호출 여부, 저장된 proposal 재사용 여부, pending·실패·완료 상태.
- 모델에 제공한 후보 ID, 모델·추론 설정, 원래 제안된 positive/negative 관계.
- 각 제안의 처리 결과: `appended`(새 관계 추가), `already_exists`(기존 관계), `rejected`(검증 거부 및 사유). 제안 0개와 아직 미처리인 작업은 별도 구분한다.
- 관계 양 끝의 Memory ID·내용·depth·Source. 같은 Source의 D0끼리, 다른 Source의 D0끼리, 추상 기억에서 새 D0로 향하는 관계를 나눠 집계한다.
- 재시작 후 같은 proposal을 다시 적용해도 최초의 append 결과를 유지하고 신규 추가 수를 중복 집계하지 않는다.

### 비용과 설정

- 기존 API 원장을 호출·추출 시도·Dream work에 연결한다. HTTP/API 호출 수와 논리 작업 수를 별도로 센다.
- Remember, Recall, Assimilation, Consolidation, embedding 등 단계별 token 사용량·실제 정산액·미정산 예약액을 표시한다.
- 한 API 호출 비용이 여러 곳에 중복 귀속되지 않게 한다. 과거 원장에서 연결을 복원할 수 없는 비용은 미귀속으로 표시한다.
- 이월된 작업은 원래 work 소유 run과 실제 과금 run도 구분한다.
- 입력 상한, observation 상한, 후보 수, Recall 상한, 모델·추론 설정, 시간대와 리포트 스키마 버전을 남긴다. 설정 변경 전후의 기록을 구분할 수 있게 한다.

## 2. 저장 설계

SQLite를 분석 기록의 원장으로 사용하고 기존 Source·Memory·proposal·API 사용량을 최대한 재사용한다. 새로 필요한 것은 호출 경계, 시도와 작업의 연결, 실제 적용 결과다.

- 호출/시도 시작을 먼저 기록하고 종료 상태를 갱신하여 중단된 작업을 미완료로 식별한다.
- D0 저장, Recall 기록, 관계 추가와 각각의 분석 결과는 가능한 동일 트랜잭션에서 확정한다.
- 특히 관계의 `INSERT OR IGNORE` 결과와 proposal 적용 기록은 원자적으로 저장한다. 현재 관계 존재 여부를 사후 조회해 최초 추가 여부를 추측하지 않는다.
- 논리 work와 실행 attempt의 식별자를 분리하여 재시도 횟수와 실제 결과를 모두 보존한다.
- 기존 DB에 추가 가능한 스키마로 설계하고, 계측 시작 시각을 기록한다. 그 이전 호출 횟수·빈 Recall·관계 적용 결과는 0이 아닌 `unknown / legacy`로 표시한다.
- 원문은 Source 파일을 참조하고 query·context 및 기억 내용은 로컬 분석 데이터에만 보존한다. 일반 콘솔 로그에 payload를 넣지 않는다.

## 3. 일별 산출물

기본 위치는 설정된 데이터 디렉터리 아래 `reports/daily/`로 한다.

- `YYYY-MM-DD.md`: 사람이 읽는 요약, 주요 분포, 상태별 개수, 상세 JSON·Source 링크.
- `YYYY-MM-DD.json`: 호출별 연결 관계와 분석에 필요한 기억 내용을 포함한 구조화 데이터. Markdown에서 생략한 상세를 보존한다.

주요 요약 지표:

| 영역 | 지표 |
| --- | --- |
| 입력 | Remember 호출 수, 신규/재사용 Source 수, 제출/신규 저장 raw 총량, 호출 크기의 p50·p90·최댓값 |
| 추출 | 새 D0 수, Source당 D0 분포, 0개 추출 수, 실패·복구 시도 수 |
| 회수 | Recall 호출 수, 빈 결과 수, 반환 D0 횟수·고유 개수, 반복 반환된 기억 |
| Assimilation | 대상 work 수, 실제 모델 호출 수, 재사용·미완료 수, 제안·append·기존·거부 개수 |
| 관계 | 같은 Source 내부/다른 Source 사이/추상 기억과 새 경험 사이의 신규 관계 수 |
| 비용 | 단계별 실제 비용·미정산 예약, Source당·처리 D0당 비용과 분모 |

일일 Recall에는 과거 생성 D0도 포함되므로 당일 생성량과 단순 나눗셈하여 회수율을 만들지 않는다. 생성일과 회수일을 함께 남겨 나중에 기간별 분석을 할 수 있게 한다.

## 4. 날짜·자동 생성·재생성

- 일자 경계는 `Engine:TimeZoneId`의 현지 날짜를 사용하고 원장 시각은 UTC로 저장한다.
- 기본 일별 활동은 실제 실행 시각으로 집계한다. Dream 대상 날짜와 실행 날짜를 함께 표시하여 밀린 Dream 비용을 새 입력 때문에 발생한 비용처럼 해석하지 않게 한다.
- 자정을 넘긴 호출은 시작일에 호출 1건을 귀속하고 완료 시각을 별도로 남긴다. API 비용은 API 호출 시작일에 귀속하며 정산 상태가 바뀌면 해당 날짜를 갱신한다.
- 서버의 별도 로컬 보고 작업이 종료된 날짜의 리포트를 만든다. Dream 성공을 생성 조건으로 삼지 않고, 실패·미완료 작업도 보고한다.
- 서버 중단 후 재시작 시 계측 시작 이후 누락된 날짜를 채우고, 늦게 완료·정산된 작업이 있는 날짜를 다시 생성한다. 무활동일과 계측되지 않은 날을 구분한다.
- 특정 날짜/기간을 수동 재생성하는 명령을 제공한다. 현재 날짜를 요청하면 잠정 리포트라고 표시한다.
- 생성 시점과 DB snapshot 범위를 기록하고 Markdown/JSON이 같은 집계 결과를 사용하도록 한다. 임시 파일에 쓴 뒤 교체해 부분 파일을 방지한다.
- 보고 작업에는 LLM/API 호출이 없으며, 리포트 출력 실패가 기억 처리나 Dream의 성공 상태를 바꾸지 않게 한다.

수동 리포트 명령은 전용 읽기 경로를 사용한다. 현재 `SqliteMemoryStore` 생성자는 스키마 초기화·Source 복구를 수행하므로 일반 서버 초기화를 그대로 재사용하지 않는다. 명령 실행으로 ingestion recovery, Dream, reindex를 시작하지 않는다.

## 5. 구현 순서와 예상 범위

1. 이벤트·결과 상태·비용 귀속·날짜 기준을 확정하고 예시 JSON/Markdown을 만든다.
2. Core의 추가 스키마와 저장 메서드, Remember/Recall 계측을 구현한다. `MemoryEngine`, `IMemoryStore`, `SqliteMemoryStore`와 호출 context/usage 연결이 주요 변경 지점이다.
3. `ConsolidationEngine` 및 관계 저장 경로에 Assimilation 시도·제안 적용 결과를 기록한다. 기존 재개·중복 방지 동작을 유지한다.
4. 읽기 전용 집계기와 JSON/Markdown 출력기를 구현한다. 이후 Server에 자동 생성과 수동 명령 경로를 연결한다.
5. 운영 문서에 경로·생성 시점·상태 정의·재생성 방법·기존 데이터 한계를 설명하고 검증한다.

이번 범위는 실사용 계측과 리포트다. observation 개수, Assimilation 정책·모델, Recall 순위, Dream 생성 규칙은 변경하지 않는다. 별도의 대시보드나 LLM 일일 평가도 포함하지 않는다. 기존 미커밋 벤치마크 작업은 보존한다.

## 6. 검증 및 완료 기준

- 같은 raw의 신규 호출·중복 호출·동시 호출·실패 후 재시도·백그라운드 복구를 구분하며 D0 생성량이 부풀지 않는지 확인한다.
- 한글·emoji를 포함한 raw 문자/byte 크기, 입력 거부, 0개 observation을 확인한다.
- 빈 Recall, 반복 Recall, 여러 depth와 순서가 보존되는지 확인한다.
- Assimilation의 빈 제안·신규 append·기존 관계·검증 거부·부분 적용 중단 후 재개를 검증한다. 재개 전후 관계 수와 최초 적용 결과가 일치해야 한다.
- 일자 경계·시간대 전환·밀린 Dream·지연 정산·서버 재시작·기존 DB를 확인한다.
- 리포트 합계가 원장과 일치하고, 같은 snapshot 재출력이 일관되며, 읽기 경로가 cognition을 호출하거나 corpus를 변경하지 않는지 확인한다.
- fake cognition과 임시 DB 기반 테스트, 기존 전체 테스트·서식 검사로 검증한다. 유료 실험은 필요하지 않다.

완료 시 실제 에이전트 호출 한 건에서 원문, 생성 D0, 이후 Recall 및 Assimilation 제안·적용 결과·비용까지 연결해 읽을 수 있어야 한다. 아직 데이터가 없는 지표는 0건 또는 미계측 상태를 정확히 구분하여 보여준다.

검증: 전체 테스트 229개 통과 후 최종 리포트 복구 보완을 적용하고, 리포트 회귀 테스트 9개를 모두 통과했다. 유료 API 호출 없이 fake cognition과 임시 DB로 검증했다.

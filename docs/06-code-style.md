# 코드 작성 기준

이 문서는 C# 코드와 테스트를 작성하거나 리뷰할 때 사용하는 기준이다. 읽기 쉬운 코드는 호출부와 구현을 읽는 사람이 적은 추측으로 동작, 비용, 상태 변화를 설명할 수 있는 코드다.

짧은 코드, 작은 함수, 적은 파일 수를 각각 목표로 삼지 않는다. 기능 테스트 통과와 가독성 검토는 별개의 확인이다.

## 작업을 시작하기 전에

1. 대상 함수의 호출부와 반환값의 소비부를 읽는다. 필요한 연산과 변경 가능한 상태를 확인한다.
2. 입력이 들어와 검증되고, 외부 자원을 사용하고, 저장되거나 반환되는 흐름을 따라간다. 실패와 취소 경로도 포함한다.
3. 현재 코드의 구체적인 문제를 설명한다. 중복 조회, 숨은 복사, 모호한 책임처럼 실제로 이해하거나 유지보수하기 어려운 지점이어야 한다.
4. 그 문제를 해결하는 범위로 변경한다. 더 이해하기 쉬워지지 않는 부분은 유지한다.

리팩터링 과정에서 동작 변경이 필요하다고 판단하면, 기존 동작과 바꿀 동작을 구분해 설명하고 그 차이를 검증한다. 코드 스타일을 이유로 도메인 정책을 바꾸지 않는다.

## 표현과 이름

- LINQ는 가급적 피하고, 반복문과 표준 컬렉션 메서드를 사용한다. 컬렉션 생성자, AddRange, Sort가 표현하는 일을 수동 루프로 다시 구현하지 않는다.
- if, else, for, foreach, while 등의 본문은 한 문장이어도 중괄호로 감싼다.
- 한 문장에 여러 상태 변경을 압축하지 않는다. 단순한 속성이나 값 계산은 간결하게 표현해도 된다.
- 이름은 역할을 구분해야 한다. 원래 실행과 비용을 부담하는 현재 실행, 입력 후보와 최종 결과를 같은 의미의 이름으로 뭉뚱그리지 않는다.
- 인덱스가 순위, 순서, 제안 식별자를 뜻하면 유지한다. 단순히 결과 목록에 추가하기 위한 인덱스와 카운터는 만들지 않는다.
- 주석은 코드가 그렇게 동작해야 하는 이유와 제약을 설명한다. 이름과 코드로 드러나는 동작을 되풀이하지 않는다.
- SQL은 선택 컬럼, 조건, 정렬, 제약을 읽을 수 있게 나눈다. 입력값은 매개변수로 바인딩한다.

기본 서식과 중괄호 규칙은 루트의 [.editorconfig](../.editorconfig)에 지정한다.

## 책임과 제어 흐름

공개 동작을 읽으면 검증, 조회, 외부 호출, 저장, 반환 순서를 따라갈 수 있어야 한다. 요청 구성과 응답 해석, 파일 보존과 DB 등록처럼 독립적인 책임은 분리한다.

함수를 추출할 때는 이름만 보고 그 작업의 책임과 결과를 이해할 수 있는지 확인한다. 몇 줄을 감싸는 도우미, 인자만 전달하는 계층, 범용 처리기를 추가하는 것으로 복잡성을 다른 곳에 숨기지 않는다. 밀접한 로직은 함께 둔다.

상태 변경과 자원 수명은 책임지는 위치가 분명해야 한다.

- DB 트랜잭션, 유료 호출, 잠금, 파일 정리의 시작과 끝을 드러낸다.
- 성공, 실패, 취소 때 누가 상태를 기록하고 자원을 정리하는지 확인한다. 같은 실패 처리를 호출자와 피호출자가 중복 수행하지 않도록 책임을 정한다.
- 실패 처리의 중복을 없애면서 원문 읽기 실패 등 기존에 처리하던 경로를 빠뜨리지 않는다.
- 실패 기록이나 자원 정리 자체가 실패하는 경로도 검토한다. 예외 전파와 재시도 횟수가 달라진다면 동작 변경으로 설명한다. 중첩 catch가 우연히 수행하던 재시도를 정상 정책으로 간주하지 않는다.
- 설정이나 외부 응답은 필요한 경계에서 검증한다. 오류는 실패한 항목과 원인을 설명해야 하며, 성공한 것처럼 기본값으로 덮지 않는다.
- 외부 응답이나 비밀값이 예외·로그를 통해 노출되지 않도록 기존 오류 전달 계약을 유지한다.

## 컬렉션 타입과 소유권

타입은 필요한 연산과 계약에 맞춰 정한다. 개수를 알고 있다는 사실만으로 배열을 선택하지 않는다.

| 필요한 일 | 선택 기준 |
| --- | --- |
| 항목을 모으거나 정렬하기 | List를 사용하고 Add, AddRange, Sort로 의도를 표현한다. |
| 결과를 순서대로 읽거나 Count·인덱스로 접근하기 | 소비부에 IReadOnlyList로 충분한지 확인한다. 생성한 List를 그대로 반환할 수 있다. |
| ID 조회 또는 중복 확인하기 | Dictionary 또는 HashSet을 사용한다. 반복적으로 다시 구성하지 않는다. |
| 고정된 수치 버퍼 또는 배열을 요구하는 API에 전달하기 | 배열을 사용한다. 필요한 경계에서 변환한다. |

반환 타입과 내부 구현 타입은 같을 필요가 없다. 이미 완성된 List를 IReadOnlyList로 전달하는 데 복사가 필요하지는 않다. 소비자가 직접 정렬해야 한다면 변경 가능한 목록을 반환하는 계약이 더 알맞을 수 있다.

IReadOnlyList는 읽기 전용 접근 계약이며 불변성이나 소유권 이전을 보장하지 않는다. AsReadOnly도 원본의 변경을 막지는 않는다. 복사와 래퍼가 필요한지는 누가 원본을 계속 소유하는지에 따라 판단한다.

- 함수 안에서 만든 결과를 반환한 뒤 생산자가 더 이상 수정하지 않는다면 그대로 전달한다.
- 외부 컬렉션을 장기간 소유하고 그 내용에 기반한 캐시를 유지하는 모델은 입력을 한 번 복사한다. 외부에서 내부 목록을 바꿀 수 없어야 한다.
- 이미 소유권이 확보된 데이터를 다른 함수로 전달할 때마다 다시 복사하거나 감싸지 않는다.
- 원본을 보존한 채 정렬하거나 필요한 일부를 선택하기 위한 복사는 목적이 있다.

예를 들어 외부 입력을 고정된 부모 목록으로 소유하는 생성자에서는 다음으로 충분하다.

~~~csharp
DerivedFrom = new List<string>(derivedFrom).AsReadOnly();
~~~

반면 완성된 cognition 결과를 저장용 제안에 넣는 경로에서는 다음처럼 그대로 보관한다. 이 계약에서 생산자는 반환한 결과와 내부 부모 목록을 이후 수정하지 않는다.

~~~csharp
var proposal = new SavedProposal(candidateIds, [], result.Value);
~~~

ToArray를 발견하면 호출부가 실제로 배열을 요구하는지 먼저 확인한다. 직접 만든 함수의 배열 요구가 불필요하다면 그 계약을 고친다. ToArray를 없애기 위해 수동 배열 복사 루프를 만들지는 않는다.

## 조회 범위와 캐시 수명

- 단건·원문별 조회에 필요한 행을 선택한다. 전체 그래프와 recall 이력을 만들고 나중에 걸러내지 않는다.
- 하나의 결과를 구성하는 기억, 부모, 관계는 같은 조회 범위와 트랜잭션을 사용한다. 관계의 소유자와 대상을 혼동하지 않는다.
- 컬렉션 전체를 재구성하거나 DB를 읽는 작업을 속성 getter에 숨기지 않는다.
- GraphSnapshot의 ID 인덱스와 MemoryRecord의 관계 목록은 생성 시 한 번 만들고 재사용한다. recall 시각만 바꾸는 복제는 고정된 목록을 공유할 수 있다.
- 캐시는 데이터가 유효한 범위에 둔다. 한 검색의 임베딩과 한 실행의 고정 스냅샷은 재사용할 수 있지만, 처리 중 바뀌는 작업 상태와 제안은 최신 상태를 읽어야 한다.
- 호출 횟수나 할당을 줄이더라도 처리 순서, 데이터 일관성, 재시도 동작을 바꾸지 않는지 확인한다.

## 이 프로젝트에서 유지할 동작

설계 배경은 [보완 설계](02-design-supplement.md), [OpenAI API 사용 확정](04-openai-api.md), [운영 안내](05-operations.md)를 참고한다.

- Remember는 정확히 동일한 raw를 LLM 호출 전에 중복 처리한다. 원문의 공백·개행을 정규화하지 않는다.
- Source 파일을 먼저 보존한 뒤 DB에 등록한다. 임시 파일 정리와 DB 커밋의 순서를 유지한다.
- Recall은 반환된 ID 전체를 검증한 다음 중복 제거와 결과 제한을 적용한다. recall이 증거나 검색 가중치를 강화하지 않는다.
- 검색의 동률 정렬, 후보 필터와 개수 제한의 순서, 그래프 방문 순서를 유지한다.
- 관계는 단방향이다. 기존 관계의 재발견으로 related_at을 바꾸거나 역방향 관계를 추론하지 않는다.
- 추상 기억은 같은 깊이의 부모와 B^depth 이상의 서로 다른 Source 근거를 가져야 한다. 사전 검증 후에도 저장 트랜잭션 안에서 다시 검증한다.
- Dream과 Meditation은 실행 시점의 입력 상한을 사용한다. 이월 작업의 근거와 제안 식별자는 원래 실행에 속하고, API 비용은 현재 실행에 청구한다.
- 제안을 적용하기 전에 저장한다. 재시도 시 이미 적용된 제안을 다시 생성하거나 임베딩하지 않는다.
- API 호출 전에 최대 비용을 예약한다. 알려진 사용량은 응답 거부·불완전·잘못된 제안을 판정하기 전에 정산하고, 사용량을 모르면 예약을 유지한다.

## 리뷰와 검증

변경 후에는 다음 질문에 답할 수 있어야 한다.

1. 읽는 사람이 무엇을 덜 추측하게 되었는가?
2. 반환 계약, 소유권, 실패 처리의 책임이 호출부와 일치하는가?
3. 복사·조회·캐시의 이유와 수명이 분명한가?
4. 기존 동작 중 유지한 부분과 의도적으로 변경한 부분은 무엇인가?
5. 그 차이를 확인하는 검증은 무엇인가?

테스트는 구체적인 입력과 관찰 가능한 결과를 검증한다. 동작 변경이나 실제 회귀 위험에 맞춰 추가하고, 구현의 루프나 내부 호출 횟수를 그대로 따라 쓰지 않는다. 기존 fixture, 실제 SQLite, 가짜 HTTP 응답을 먼저 활용하며 단순한 검증을 위해 새 mocking 계층이나 reflection 장치를 도입하지 않는다.

서식 변경이나 단순한 이름 변경마다 테스트를 추가할 필요는 없다. 기존 테스트를 활용하되, 통과했다는 사실로 설계와 가독성 리뷰를 대신하지 않는다. 결과를 보고할 때는 바꾼 이유, 유지한 계약, 검증 결과를 함께 적는다.

~~~powershell
dotnet format whitespace LongJourney.slnx --no-restore
dotnet format style LongJourney.slnx --no-restore --diagnostics IDE0011 --verify-no-changes
dotnet test LongJourney.slnx --configuration Release --no-restore
~~~
